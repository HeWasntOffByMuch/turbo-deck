# 101 — A softer edge nobody asked the scene for

Step 9 of the hike arc (spec 093). Behind `HikeSettings.softShadows`, off by
default, with `shadowPcfRadius`.

## What the brief asked for, and what was already there

> Shadows: single tight orthographic shadow map, fixed sun direction,
> Poisson-disk PCF.

Two of those three already exist and are better than the request:

- **A single tight orthographic shadow map** is spec 045. It is not merely tight,
  it *follows the view* — centred on the camera's target with extents scaled from
  the zoom, so the resolution is spent on ground somebody is looking at. A map
  sized once for the world ring would put a ten-unit texel under every shadow.
- **A fixed sun direction** would be a regression. Spec 047 gives the world a
  day/night cycle, and the sun's elevation is what a player reads the time of day
  from. `shadow.ts` already handles what a moving sun does to shadows: a floor on
  the casting elevation so an evening shadow is long rather than infinite, a
  contrast fade toward dusk, and a terminator fade so the sun/moon handover
  passes through zero instead of reversing.

So this step is the third item only: **Poisson-disk PCF**, and the switch to turn
it off.

## Why it is off by default, and stays off

Spec 045 chose `BasicShadowMap` at 1024 deliberately, not for want of anything
better. Every shadow edge lands on a texel boundary and stays hard, which is the
same register as the posterized, dithered, `image-rendering: pixelated` frame the
shadow lands in. A soft penumbra would be the one smooth gradient in the picture.

That argument still holds. This exists so the choice can be seen rather than
assumed — which is the whole premise of the arc — not because the default is
wrong.

## How it is switched, and why there is no new uniform

The filter branches on `shadowRadius`, which three.js already plumbs from
`light.shadow.radius` into every lit material's `getShadow`, whatever the shadow
map type. `BasicShadowMap` ignores it today; this gives it a meaning.

That is worth spelling out, because the obvious implementations are all worse:

- **Switching `renderer.shadowMap.type`** is a global that is compiled into every
  shader, so throwing the switch means recompiling every material in the world —
  and none of the built-in types is a Poisson disk anyway.
- **A new uniform** cannot reach the built-in materials. Uniform groups are merged
  into `ShaderLib` when three.js loads, before any of our code runs, so a uniform
  added afterwards never propagates.
- **Patching every material's `onBeforeCompile`** means finding all of them —
  ground, walls, props, units, critters — and composing with the patches already
  there. Spec 100 had to do exactly that dance for one material, and it is one
  material's worth of risk each time.

Instead `THREE.ShaderChunk.shadowmap_pars_fragment` is patched **once**, replacing
the unfiltered branch with a choice between the single tap it already did and the
Poisson taps. Every material that includes the chunk gets it, which is all of
them, and the switch is a JavaScript property write per frame: no recompiles, no
new uniforms, nothing to enumerate.

The patch is idempotent by a module flag. Applying it twice would redefine a GLSL
function, which fails to compile — and three.js logs a failed compile and carries
on, so it would be silent.

## The disk

Twelve points, generated by Mitchell's best-candidate over the unit disc with the
repo's seeded PRNG, and emitted into the shader as constants from the same array
the tests assert on. Generated rather than pasted so the properties can be
checked instead of trusted.

**Not rotated per pixel.** Rotating the kernel by a per-pixel hash is the standard
way to trade banding for noise, and it is wrong here for exactly the reason spec
045 gave: a noise pattern that changes every frame is a shimmer, and this frame is
quantized and nearest-neighbour upscaled, so the shimmer would land on whole
pixels at once. A fixed disk gives a penumbra that is stable frame to frame and
banded at worst.

## Invariants, and where each is checked

Headlessly, in `poisson.test.ts`:

- every point is inside the unit disc;
- no two points are closer than a stated minimum separation — the property that
  makes it a Poisson disc rather than twelve random points, and the one a
  hand-pasted table quietly fails;
- the set is roughly centred, so the penumbra does not drift to one side of the
  caster;
- it is deterministic for a seed, and a different seed gives a different set;
- the GLSL carries the same numbers as the array, checked by parsing them back
  out rather than by string match.

On a real GPU, in `scripts/probe-shading.ts`, with a caster over flat ground:

- with the radius at 0 the shadow edge is **hard**: almost no pixel sits between
  fully lit and fully shadowed;
- with the radius up, the count of partially-shadowed pixels rises by more than an
  order of magnitude — that is the penumbra, measured;
- the shadow does not **move**: its area changes by only a few percent, because a
  filter is meant to soften an edge and not to grow or shrink the shape;
- and open ground far from any caster is **byte-identical**, because a filter that
  dims the whole scene is a filter that is sampling outside the frustum test.

## Out of scope

- The point-light (torch) shadows, which go through `getPointShadow` and a cube
  map. Softening those is a different chunk and a different cost.
- Contact-hardening / PCSS. The blocker search that makes a penumbra widen with
  distance is several times the cost and would be measuring a shadow map this
  world deliberately keeps small.
